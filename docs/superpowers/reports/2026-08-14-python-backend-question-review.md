| 60 | 0.5 | 0.3 | CLI 플래그 암기 (게다가 정답 중복) |
| 63 | 0.5 | 0.3 | print vs logging — 상식 |
| 38 | 0.5 | 0.3 | POST 가 멱등이 아니다 — 암기 |

### 0.9 급 부족분

위 재평가를 적용한 뒤 분포(실계산):

| 대역 | 목표 | 현재 | 재평가 후 |
|---|---|---|---|
| 0.1-0.2 | 10 | 10 | 10 |
| 0.3-0.4 | 25 | 26 | **43** |
| 0.5-0.6 | 30 | 41 | 26 |
| 0.7-0.8 | 25 | 21 | 20 |
| 0.9 | 10 | 2 | **1** |

- **재평가 후 0.9 급 예상 개수: 1개** (index 81). 후하게 잡아 87 을 포함해도 2개.
- **부족분: 9개** (관대하게 봐도 8개)
- **핵심 결론: 난이도 재평가로는 해결되지 않는다. 오히려 악화된다.** 현재 0.9 로 표기된 2개(67·68)는 실제로 0.3~0.4 급 암기 문항이고, 0.5-0.6 대역 41개 중 상위로 올릴 만한 것은 5개뿐인 반면 아래로 내려야 할 것은 12개다. 이 100문항 세트에는 **숙련자 변별용 문항이 사실상 존재하지 않는다**. 유일한 해법은 **0.9 급 신규 문항 9개 추가 + 0.3-0.4 대역 과잉분 18개 제거·상향 대체**다.

#### 추가로 필요한 문항이 다뤄야 할 개념 (9개 제안)

기존 100개가 이미 다루는 개념(GIL·N+1·mutable default·캐시 스탬피드·alembic heads)의 재탕은 피하고,
**"동작을 알면서도 틀리는" 지점**을 노린다.

1. **`asyncio.create_task()` 의 강한 참조 미보관 → 태스크가 GC 에 수거되어 조용히 사라지는 실패 모드**
   (CPython 공식 문서가 "Save a reference to the result of this function" 을 경고하는 바로 그 케이스. 로그도 안 남는다)
2. **`transaction.on_commit()` 훅의 실행 시점 — 중첩 `atomic` 의 savepoint 와 `TestCase` 안에서는 아예 실행되지 않는 함정**
   (index 21·81 이 다루는 rollback 과 겹치지 않는 별개 축. "테스트는 통과하는데 운영에서만 이메일이 안 나간다"의 원인)
3. **Django `select_related` 가 통하지 않는 케이스 — 역참조(reverse FK)·M2M 에는 쓸 수 없고 `prefetch_related` 여야 하며, nullable FK 에서는 INNER 가 아닌 LEFT OUTER JOIN 이 된다**
   (index 17·27·80·83 은 전부 "N+1 이 난다"만 묻는다. 처방이 언제 **안 먹히는지**를 묻는 문항이 없다)
4. **SQLAlchemy `expire_on_commit=True` 기본값 — `commit()` 직후 인스턴스 속성 접근이 추가 SELECT 를 유발하고, 세션이 닫힌 뒤에는 `DetachedInstanceError` 가 터진다**
   (index 40·86·91 은 세션 수명주기의 표면만 다룬다)
5. **`QuerySet.iterator()` 와 `prefetch_related` 의 상호작용 / `.count()` vs `len(qs)` 의 캐시 동작 차이**
   (지연 평가를 index 0·16 이 다루지만 둘 다 "언제 실행되나" 수준. 캐시가 **재사용되는지**를 묻는 문항이 없다)
6. **gunicorn `preload_app=True` + fork — 마스터에서 열린 DB 커넥션·난수 시드가 자식 워커에 상속되어 깨지는 고전적 실패 모드**
   (index 57·67 은 워커 **개수**만 다룬다. `preload_app` 은 메모리 절약이라고 켰다가 사고 나는 대표 설정)
7. **Celery `acks_late=True` + 브로커 `visibility_timeout` — 장시간 태스크가 visibility timeout 을 넘겨 다른 워커에 중복 배달되는 조건**
   (index 46·85 의 "멱등성이 없으면 위험"보다 한 단계 아래 — **왜 재시도가 아닌데도 중복 실행되는가**)
8. **FastAPI `response_model` 이 서브클래스 반환값의 필드를 조용히 잘라내는 동작 / `Union` 응답에서의 검증 순서**
   (index 33·34 는 "지정하면 검증된다"까지만 간다. 데이터가 **말없이 사라지는** 쪽이 진짜 함정)
9. **`asyncio` 태스크 취소 시 `finally` / `async with` 정리 코드의 실행 보장과 `CancelledError` 재전파 — `except Exception` 이 `CancelledError` 를 잡지 못하는(3.8+ `BaseException` 승격) 이유**
   (index 75 가 `except Exception` 의 예외 계층을 오답으로만 스치고 지나간다. asyncio 와 결합하면 명확한 0.9 급)

각 문항은 CODE_READING 형태로 만들면 난이도가 안정적으로 확보된다(위 재평가에서도 상위 대역은 대부분 CODE_READING 이었다).
**단, 신규 문항 작성 시 위 ★ 지적을 반드시 적용할 것 — 오답 3개를 정답과 같은 길이·구체성으로 쓸 것.**

## 전체 인상

**지금 상태로는 진단 도구로 쓰기 어렵다. 형식 게이트는 통과했지만 두 가지 구조적 결함이 있다.**

**1) 변별력이 위아래 양쪽에서 무너져 있다.**
"가장 긴 보기 찍기"만으로 **77점**이 나온다(기존 5트랙은 35~58). 이건 개별 문항의 흠이 아니라 생성 방식의 문제다 —
정답은 메커니즘을 자세히 서술하고 오답은 "정상적으로 조회됩니다" 한 줄로 끝내는 패턴이 100문항 전체에 걸쳐 반복된다.
적응형 진단은 응시자의 응답으로 능력을 추정하는데, 능력과 무관한 표면 단서로 정답률이 결정되면 **추정치 자체가 오염된다.**
2026-08-13 의 "선택지 한 벌 공유" 사고와 성격이 다르지만 귀결은 같다 — **문항이 능력을 재지 못한다.**

**2) 천장이 없다.**
상위 대역이 숫자로만 채워져 있었다. 0.9 로 표기된 2개는 실제로는 0.3~0.4 급 암기 문항이고,
정직하게 재평가하면 0.9 급은 **1개**뿐이다. 이 트랙은 실력 있는 응시자에게 낼 문항이 없다.
적응형 진단이 상위에서 낼 카드가 떨어지면 결과가 위로 뭉개진다는 지적은 정확했고, 실측하니 예상보다 심하다.
반대로 0.3-0.4 대역은 재평가 후 43개로 목표(25)의 1.7배다. **이 세트는 전체적으로 쉬운 쪽에 몰려 있고, 난이도 라벨이 그것을 가리고 있었다.**

**잘 된 부분도 분명하다.** CODE_READING 30문항(index 70~99)은 **문법 오류가 한 건도 없고**(선행 문자 탈락 전례 없음),
다루는 함정도 실무적이다 — atomic 재진입(81), 시그널 재귀(84), Depends 캐싱(87), verify_exp(90), BackgroundTasks 예외(98)는
그대로 쓸 수 있는 좋은 문항이다. 트랙 경계 위반도 **0건**으로, pandas·모델 학습이 새어 들어오지 않았다.
정답키가 실제 오답을 가리키는 치명적 오류도 **0건**이다.
